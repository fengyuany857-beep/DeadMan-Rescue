# 死人开关自救模块设计稿（DeadMan Rescue）

状态：按 CODEX-AUDIT.md 修订的设计稿，未开发、未安装；本次仅修订文档，不代表部署或真机验收通过。日期：2026-11-16。
对象：黑鲨 5（SHARK PAR-A0，Android 12，JoyUI，高通平台，Magisk Alpha 31100）。
背景故障：插电状态下软件重启间歇性落入关机充电层，系统不起来，只能真人长按电源键；2026-11-16 12:19–12:26 有人值守受控复现一次。完全关机时无任何已验证的远程开机通道。
证据边界：接受故障原型、T1 root 读写清成功及 RescueX 已在守护的既定事实。除第 12.5 节列出的实测外，所有本机特有行为均为「T2/T3 待裁决」，包括信号时序、关机保留、充电层唤醒、原因映射和响后状态；表中协议与数值是设计要求，不是实现或实测结果。

## 0. 一句话原理

活着时续期一笔未来 RTC 唤醒；若最后一笔成功布防在故障关机/充电层中被保留并被固件认可，到点尝试触发上电（T2/T3 待裁决）。正常关机/重启以自有入口预登记注销或改签；启动后先清残、再幂等核销、再按预算决定是否新布防。无登记只能说明缺少可信意图，不能单独证明曾由 RTC 救起。

## 1. 目标与非目标

目标：

- G1a 唤醒触发时限：在 RTC 供电、关机层支持、最后一笔布防有效且未被改写/调时破坏的前提下，以 WINDOW=600 秒为最后成功写入后的名义触发窗口。理想连续续期时，故障发生后的硬件剩余量约 540–600 秒；这不是无条件上界，需计入采样、调度和写入误差，并由 T2/T3 裁决。
- G1b 健康启动时限：从实际触发上电到系统完成健康启动另计启动预算。原稿约 60–120 秒只能作待重新量测的参考，不能承诺 10 分钟内进系统。若将来要求总计 10 分钟，须在实测启动和抖动预算后另行修订 WINDOW，本轮不改数值。
- G2 自发重启落入充电层或异常断电后也尝试恢复，前提是 RTC 仍有供电、硬件状态可保存且所在关机/充电层支持该通道。电池真耗尽、持续通电挂死、固件不认可唤醒时不保证恢复；本机层间支持为 T2/T3 待裁决。
- G3 条件式正常关机承诺：仅对受支持的自有预登记入口，在禁止续期持久化、注销清槽读回成功并提交后，保证本模块不主动保留或重建该笔闹钟。其他入口、外部写者或绕过收尾存在误启动风险；开机后的 REOFF 只是补偿，不能兑现「绝不被拉起」。
- G4a 硬件单次：中断、驱动使能、PMIC 和固件关机唤醒状态是否一次性，均为 T2/T3 待裁决；不以槽为空或旧值过期推导固件全部解除。
- G4b 事务单次：持久化 arm_id 每笔只消费一次，成功清槽后不复用旧 arm_id；清残与核销各阶段可重放，不因同 boot 拉活重复消费或自动关机。
- G4c 故障救援预算：独立跨 boot 限额、冷却与稳定运行确认阻止软件自动反复布防；耗尽即解除武装并停用。预算不能约束未进入用户空间时的固件重复行为，后者仍待实测。
- G5 全程留痕：布防、注销、救援、对账均有事务身份和结果；存储有界，故障可观察，不能落盘时不报告成功。

非目标：

- 不处理卡米/开机循环的主救援，由 RescueX 主责（第 8 节）。
- 不处理「系统挂死但仍通电」；外部断电手段如智能插座仍是另一未定候选。
- 不修补 boot.img，不改引导层；Magisk Autoboot 路线因改 boot 且语义冲突不采用。

## 2. 硬件层：RTC 布防通道

首选槽为 `/sys/class/rtc/rtc0/wakealarm`。本模块内部统一锁只能约束合作进程，不能给全局单槽提供硬件独占。已知 JoyUI 定时开关机、关机闹钟须关闭；不能由一次空槽证明长期无人写。唯一竞争策略为**冲突即停用**：不覆盖外部闹钟，不在下一轮抢回；记录读值和预期值后进入 QUARANTINE，停止自动布防，已知属于本模块的旧槽按解除武装协议清理。无法确认归属的非空槽须由可信控制入口确认处置，不盲清。

### 2.1 通道与参数契约

| 项目 | root 直写 sysfs（主路） | PowerOffAlarm（备选） |
| --- | --- | --- |
| 已有证据 | T1 本次 `0 → +7200 → 读回 → 0 → 空槽` 成功 | 组件在机，未调用 |
| 时间输入 | `+N` 为写入时相对 RTC 的请求秒数，不写系统 Unix epoch；先清再写并验证 | API、时间基准、权限、私有持久状态及取消方式须离线审阅并另建契约；本机 T2/T3 待裁决 |
| 600/240 的口径 | WINDOW/REBOOT_WAKE 是通道请求量，最终硬件剩余量另采样验证 | 不直接沿用请求量；须按实际变换换算，记录请求量与最终硬件剩余量 |
| 提前量 | 原有生产请求下限 240 秒保留为试验起点；T1 未证明直写存在厂商减 60 秒行为 | 审计所述高通实现有减 60 秒及拒绝过近时间的机制，是否适用于本机接口、变换顺序和拒绝边界均为 T2/T3 待裁决；不得双减 60 秒。若请求 240 最终为 180，仅作风险示例 |
| 启用条件 | 完成主机验证及有人值守 T2/T3 后才可持续布防 | 不是只换一条命令；独立验证设置、读取、取消、关机侧行为后重新通过 T2/T3 |

一次只允许选择一个通道，禁止两路同时兜底。两路都不通则 RTC 设计不成立；其他路线须另议，不在本轮新增。

### 2.2 RTC 采样、跳变和槽竞争

`+N` 只避免写入时误用系统 epoch，不能保护武装期间的 RTC 调时。每轮操作前后配对记录 RTC since_epoch 与本 boot 单调时钟（采用固定且含休眠口径的单调时基），并留墙钟作展示。用单调时钟包围 RTC 读取以形成采样区间；比较相邻 RTC 增量与单调增量，容差须由采样耗时、量化和漂移试验确定，不接受任意差值。

写入后的读回剩余量按 RTC 前后采样区间校验，包含命令流逝和允许误差；不拿系统 epoch 比较。超容差、RTC 重置、不可读或槽与上笔已验证值不符，立即停止续期并记录 UNKNOWN/FAULT 或冲突 QUARANTINE，不下轮覆盖。对确认自有槽尝试清除并读回；不成功则保护状态仍为未知。守护死亡、停机和关机过渡无法靠周期采样检测或纠正；系统校时是否触及 RTC、闹钟是否随之调整、厂商末期覆盖/清槽、长期漂移及关机保存性全部为 T2/T3 待裁决。

## 3. 模块形态

Magisk 模块，纯 `/data/adb` 层，不动 boot 镜像：

- `post-fs-data.sh`：最早可用且权限/存储就绪时，以同一锁执行轻量清残/恢复阶段，不开启续期或 REOFF；若未能运行，late_start 重试，不能保证在用户空间以前补救。卡米备份计数层默认关。
- `service.sh`：late_start 拉起守护，先恢复和对账，再允许续期；单实例不能仅靠 PID 文件判断。
- 守护：周期 60 秒，按单调时钟调度，实测开销后定版，不预称「可忽略」。
- 状态目录：`/data/adb/deadman-rescue/`，模块目录之外，仅防通常升级替换，不防清理模块/root 误删。
- 唯一权威记录：逻辑 `registry` 事务账本，由 HEAD 指定的校验快照与有界尾日志组成（第 5 节）。`state`、单独 seq 文件、boot 标记、心跳视图和诊断 log 都是可重建缓存，不反向覆盖权威账本。
- 守护、命令入口、早期清残、升级/禁用/卸载和监督器共用固定锁 `/data/adb/.deadman-rescue.lock`；锁在状态目录外，避免目录被删产生两套锁。锁持有期间检查锁 inode、目录身份、实例代次和 stop_generation；身份变化即停止操作，不能自动另建锁继续。
- 监督可选，默认只报告；按第 8 节显式许可才可拉活，不能替停用模块布防。

### 3.1 权限与输入边界

目录 root:root、0700；账本、配置、锁及临时文件 root:root、0600，`umask 077`。固定绝对路径，校验所有者和类型，拒绝状态/命令路径中的软链接及异常可写父目录；已知 sysfs rtc0 设备链接只按固定预期设备路径校验，不对任意外部路径 chmod/chown。临时文件在同目录安全创建。

状态只按数据解析，检查版本、长度、字段类型、取值范围及 boot_id/arm_id/事务关联，不 `source`、`eval` 或拼接成 shell 命令。AutoJs6/Muse 仅经鉴权 root 固定命令和参数白名单调用；不开放无鉴权广播、普通应用可写的指令队列、网络监听或日志外发。不能隔离恶意 root，也不能阻止其他合法 root 写槽。

### 3.2 存储限额

以下为新增设计起始上限，需主机满盘/轮转验证，并非既有实测值：

| 对象 | 字节与文件上限 | 达限处理 |
| --- | --- | --- |
| 权威快照 | 每份 1 MiB，稳态 1 份；切换临时保留旧/新各 1 份 | 压缩已完成事务，保存状态、代次、消费水位、预算和所有未完成事务 |
| 权威尾日志 | 每份 1 MiB，稳态 1 份；切换时旧/新各 1 份 | 提前快照压缩，完整记录最长 8 KiB；预留 64 KiB 给停用/故障收尾，不承诺满盘仍可写 |
| 诊断日志 | 4 个文件，每个 256 KiB，合计 1 MiB | 限频合并重复故障，轮转删除最老已完成诊断 |
| 已完成事务归档 | 2 个文件，每个 1 MiB，合计 2 MiB | 只删已快照覆盖的完成历史，不删未完成事务或消费/预算依据 |
| 全目录 | 8 MiB，包含缓存、旧代和临时文件 | 预检峰值空间；缓存与临时空间合计不超过剩余 1 MiB；收尾前不接纳新布防 |

总限额包括快照/尾日志切换时各两份的峰值。未完成事务不因限额被丢弃；压缩仍放不下则停止新增事务、持久停用并进入 FAULT。每轮检查目录身份和可用空间；缺目录不自动初始化为新安装。ENOSPC、EIO、任何 fsync/rename/目录同步失败均使相关提交失败，禁止继续新增武装或返回注销成功；保留最近有效代和恢复阶段，具体见第 11 节。

## 4. 守护进程主循环（活着时）

每 60 秒一轮，始终遵守第 5 节事务协议：

1. 获取共享锁，归约权威状态。只有已显式启用、许可代次匹配、预算已预留且状态允许的 ARMED（或已获准从 DISARMED 首次布防）可操作。STAND_DOWN、UNKNOWN、RECONCILING、FAULT、QUARANTINE、维护/禁用/升级/卸载均禁止续期。
2. 锁内复查实例代次、stop_generation、监督许可、温度/电量与冷却门槛；不得使用锁外读到的旧许可。off 等入口先在同锁下增加并持久化 stop_generation，后续旧轮次失效。
3. 先读槽与 RTC/单调配对值，核对自有槽及跳变。冲突即停用（第 2 节）。新事务含旧 arm_id、新 arm_id、目标请求 WINDOW=600、目标 RTC 区间和采样，持久 PREPARED 后进入 ARM_PENDING。
4. 清 0、读回空、写 `+WINDOW`、读回验证；每步检查退出码。清后写不是原子替换：从清成功至新写成功存在无闹钟窗口，被杀可能漏救，内部锁也挡不住外部抢槽；本轮不假定其他更新接口可用。
5. 成功读回后写 COMMITTED，再更新心跳缓存，转 ARMED。每次真实硬件变更都有权威事务，只有诊断心跳可节流，不能省略布防账目。
6. 单次任一步失败即停止本轮，标记阶段与硬件状态（已知空/已知值/未知），不假定旧闹钟还在。回到恢复读槽流程，禁止盲目清写。只允许在同 boot、无停用/冲突、持久层健康且读回已解释的情况下，按有界恢复事务重试；身份/时钟不确定则直接隔离。持久层或清残验证失败立即 FAULT，不必等三次。
7. 计数只在完整成功提交后归零；可恢复 RTC 操作连续失败达到 WRITE_FAIL_MAX=3 时，先持久增加停用代次并停止所有自动续期，尝试清理确认自有旧槽并读回，留清理待办。报警区分「已解除」与「槽未知/可能残留」；不声称旧值至多响一次。FAULT 持久且监督器不得清除；可信控制入口修复、清槽验证后才可重新许可。

报警通过本地状态/限频日志及 Muse 既有只读巡检观察故障码、最后成功时间、保护剩余区间、预算和清槽结果；落盘失败时同时返回错误并向仍可用的进程输出暴露故障，不伪造持久记录。没有可用观察者时不能保证报警送达。

## 5. 登记制（用户提出的编号制，形式化）

### 5.1 身份、归约与完整性

每条记录含 `version、instance_generation、seq、tx_id、phase、type、operation、source_boot_id、arm_id、previous_arm_id、consumed_by_boot_id、stop_generation、intent/target、channel、RTC/单调采样、请求量/读回、预算、结果/错误、prev_checksum、length、checksum`；不适用字段显式为空。墙钟只供展示。type 保留 HEARTBEAT、INTENT、BOOT、RESCUE，并加入事务/停用/取消/恢复记录；phase 为 PREPARED、硬件阶段证据、COMMITTED 或 FAULT。完整性校验用于发现损坏，不是抵御恶意 root 的认证。

- seq 仅在验证过的实例代次和事务链中递增，arm_id 由实例代次和布防事务身份组成，不依赖可损坏的单独 seq 文件。INTENT 绑定来源 boot、对应 arm_id 和目标，消费时写 consumed_by_boot_id。续期/改签提交同时把 previous_arm_id 标为已替代终态；已替代值不再作为有效救援意图复用。reboot 登记关联改签产生的新 arm_id，off 关联待清的旧 arm_id（原本无武装时可为空并记录已验证空槽）。
- 每个 boot 的 BOOT 对账键幂等；同 source_boot_id 的 INTENT 不作为下一次开机登记消费。只按快照与有效事务归约，不看「末条 type」。BOOT/RESCUE/诊断尾记录不会遮住未完成 INTENT。
- 日志采用限长完整行、长度及前向校验链；读取到坏尾时只保留已验证前缀并记录偏移，隔离损坏证据，在持锁且有空间保存证据时才截断不完整尾。中段损坏、未知版本、代次冲突或无法解释的硬件动作一律 UNKNOWN/QUARANTINE，不靠截断伪装完成。
- 只取已验证链内最大 seq。整体备份回滚可能同时回滚所有文件，无法保证绝对单调或检测一切回滚；发现/无法排除回滚时建立新实例代次、隔离旧意图，清残验证并经可信入口重新启用，不据旧 INTENT 自动关机。
- state 缓存可落后并重建；若缓存超前、代次不符或权威链本身冲突，先 UNKNOWN 检查，不能选一个看起来新的文件继续布防。

### 5.2 持久化与跨 RTC 事务

唯一权威是 HEAD 选中的快照和尾日志链。尾日志按完整记录追加并 fsync，追加失败不算提交；首次建文件及目录变更须同步父目录。缓存可用同目录临时文件写入、fsync、rename、父目录 fsync，但不参与决定事务成功。

快照/轮转在同锁下进行：从已验证链生成新代快照及新尾日志，保留未完成事务、已消费 arm_id 水位/去重信息、boot 对账键、预算、停用代次和旧意图隔离信息；文件分别 fsync，再同步目录。写新 HEAD 临时文件并 fsync、rename、父目录 fsync 后才切换权威代；此前旧代仍有效。切换后才能删除已覆盖旧文件，并再次同步目录。恢复只选有效 HEAD 指向的完整链，不扫描孤儿文件猜「最大代次」；HEAD 不确定则 UNKNOWN。多个文件 rename 不能形成与硬件同步的原子事务。

所有改变槽位的入口在同锁下执行：

1. 持久 PREPARED：保存操作、旧/新 arm_id、目标、预采样及恢复策略；off/维护/生命周期收尾还须先持久禁止续期代次；新的保护会话须先预扣救援额度。
2. 执行硬件动作并检查返回值、读回；在账本记录 CLEARED_VERIFIED 或 ARMED_VERIFIED 阶段。清槽读回仅证明当前可见接口，固件侧含义为 T2/T3 待裁决。
3. COMMITTED 后才报告成功；启动对账必须先清旧槽读回并持久记录，再提交 consumed_by_boot_id 和分类。FAULT 保存阶段与观察值；不能落盘则保留最后持久 PREPARED，恢复按不确定事务处理。

### 5.3 事务与崩溃恢复表

| 中断点 | 可依赖内容 | 恢复动作与状态 |
| --- | --- | --- |
| PREPARED 前或 fsync 未成功 | 仅旧已提交链；硬件不应开始改变 | 停自动动作、读槽；若与旧账不符则 UNKNOWN，不能凭心跳猜测 |
| PREPARED 后、清槽前 | 目标/旧槽身份与停止代次已持久 | 先读硬件；off/维护继续幂等清槽；续期不盲重写，转 ARM_PENDING 解释现状 |
| 清成功、写前或清槽证据未落盘 | 可能已无闹钟 | 读回确认空/未知，明确无保护窗口；同 boot 且满足第 4 节重试条件才可新事务布防，否则 FAULT；跨 boot 先清残对账 |
| 写成功、验证或 COMMITTED 前 | 可能有未提交武装 | 读回与 PREPARED 目标匹配且同 boot、时基可信、无停止代次变化才可补提交；不匹配/跨 boot 先停用并按归属清残，不按旧 HEARTBEAT 分类 |
| 布防 COMMITTED、缓存更新前 | 权威布防有效，缓存陈旧 | 重建缓存；同 boot 不重复 BOOT、核销或扣额；新 boot 走清残对账 |
| off 禁止续期后、清槽/读回失败 | 停用已生效，闹钟可能残留 | 不执行受支持关机命令、不返回注销成功；重试解除武装或人工收尾，FAULT |
| 清槽验证后、消费提交前 | 原 arm_id 及清残阶段尚在 | 下次先重读并必要时再清，再补一次消费；不得先丢核销依据 |
| 消费 COMMITTED、BOOT 缓存前 | arm_id 已被指定 boot 消费 | 仅重建结论，不重复消费、不重做 REOFF |
| REOFF 请求持久化后、命令前/后失联 | 是否执行关机可能未知，尝试额度已用 | 不再自动调用关机；停用/隔离，留请求未确认状态，等待可信确认 |
| 快照或 HEAD 切换中 | 旧有效 HEAD 或新完整 HEAD | 只按有效指针恢复；同步结果不确定则 UNKNOWN，保留两代，不启用 |
| ENOSPC/EIO、目录丢失、链损坏 | 可能无法持久停用，硬件不确定 | 当前进程立即停写槽、通知错误；读硬件并按第 11 节解除武装，不盲建新账/续期 |

重放只重试读槽、已知自有槽的清除及持久核销等幂等动作；重启/关机命令不是可盲重放动作。锁不消除断电、强杀或跨硬件事务窗口，不能同时保证所有故障下绝不误救和绝不漏救。

## 6. 关机拦截（如何登记）

### 6.1 自有入口预登记：主路

Muse/脚本使用鉴权的固定 root 入口，将登记与实际命令封装在同一协议中。只有入口确认前置事务成功后才发起实际操作：

- off：锁内持久提高 stop_generation、INTENT(off) PREPARED → 清槽并读回 → COMMITTED → 返回注销成功并调用固定 shutdown 命令。清槽失败不继续执行受支持关机；用户若仍决定强关，须明知残留风险。
- 普通 reboot：持久 STAND_DOWN 和 INTENT(reboot) → 按 REBOOT_WAKE=240 请求改签、验证和提交 → 固定普通重启命令；改签失败返回错误，不伪称有保护。
- 维护/特殊重启：持久维护 STAND_DOWN，清槽验证后才进入目标；不得给 recovery/bootloader 改签普通 +240。

命令明确返回失败且可信确认仍在原 boot、操作未发起时，追加 CANCEL（关联原 INTENT），保持停用，清理已改签槽并验证；经显式 resume 许可、预算和安全门槛后才新建布防事务。只登记却未执行、命令超时或返回结果未知时，不自动取消/续期；设置 INTENT_WAIT 超时状态并限频提示，等待人工或可信入口确认。取消不得删除历史 INTENT。

### 6.2 SIGTERM trap：尽力补充

Magisk 拉起 shell 不等于 init 独立服务。是否收到信号、何时能执行 trap、等待子命令时如何响应、属性是否仍可读、磁盘能否同步均为 T2/T3 待裁决；SIGKILL 没有 trap。trap 不作为 G3 主保证。

sys.powerctl 仅是瞬时线索，不是可靠持久事件日志；T1 只证实运行期为空。先按逗号拆 action 与 target/reason，保留原值，使用已验证白名单，不仅做全串等号：

| 输入 | 处理 |
| --- | --- |
| `shutdown`、`shutdown,<reason>` | action=shutdown，按 off 尽力注销；reason 仅记录、严格校验，不执行文本 |
| `reboot`、`reboot,<已验证普通 reason>` | 普通重启登记改签，前提是目标白名单无歧义 |
| `reboot,recovery`、`reboot,bootloader` 及已知维护目标 | 维护 STAND_DOWN、清槽验证，禁止普通改签 |
| reboot 未知 target/reason、未知动作、畸形字段 | 保守维护 STAND_DOWN、停止续期，按自有槽清除协议处置，不猜普通重启、不代发命令 |
| 空值/仅 SIGTERM | 不据此推断关机意图；作为停止守护处理，持久停用并尽力清自有槽，不能制造 off/reboot 登记或 REOFF 依据 |

与已完成的同源预登记幂等合并，trap 不重复改签或覆盖更强的停用状态。系统菜单、厂商快捷入口、其他 root 命令未自动纳入支持范围，覆盖度及厂商集合为 T2/T3 待裁决。用户长按希望关机与异常消失可能不可区分；希望保持关机须先通过停用入口清槽读回，再强关。电池耗尽不能假设可执行登记。

### 6.3 耗时预算

临终路径包括锁等待、PREPARED/fsync、清槽或清写、读回、COMMITTED/fsync，必要时目录同步；不保证毫秒完成。预建目录并验证权限，trap 不联网、不轮转、不长等锁。主机注入验证后，在有人值守采样中填写下表，定版前各项均未测：

| 阶段 | 需量测项目 | 超时后行为 |
| --- | --- | --- |
| 等锁与校验 | p50/p95/p99、最大观察耗时、硬超时 | 不越锁写槽，返回失败并保留阶段 |
| 持久 PREPARED/停用 | 同上，含 ENOSPC/EIO | 不开始新硬件动作，不报成功 |
| 清/写/读回 | 同上，分别统计 off 与 reboot | 状态未知，进入恢复，不假设旧值保留 |
| 提交与完整链路 | 文件/目录 fsync 及总预算 | 不声称可在强杀前必然完成 |

预算、INTENT_WAIT 和锁超时须在真机持续布防前实测定版，未定版不能把 trap 覆盖作为能力保证。

## 7. 开机对账（开机后清残、幂等核销与受限补偿）

### 7.1 状态与转换表

状态含 UNKNOWN（无法可信归约）、DISARMED（已验证解除）、ARM_PENDING（持久布防准备、硬件未提交）、ARMED（已提交武装）、STAND_DOWN（持久禁止续期，含维护/等待操作）、RECONCILING（清残与核销中）、FAULT（操作故障停用）、QUARANTINE（身份/时基/竞争等不可信隔离）。以下优先处理故障/停止条件，再处理意图与原因；正常续期不能绕过这些状态。

| 入口/事件 | 转换及确定规则 |
| --- | --- |
| 首次安装、空账本 | UNKNOWN → 读取槽；只有可信新安装且空槽验证后建立初始代次到 DISARMED。非空且归属未知则 QUARANTINE，不默认覆盖；显式启用后才 ARM_PENDING → ARMED |
| 状态目录丢失、坏账本、坏尾、seq 损坏/回滚、未知版本、缓存冲突 | UNKNOWN，按第 5 节恢复有效链并读硬件；无法恢复则隔离旧意图，不猜用户意图、不自动关机；可信恢复入口清残验证后 DISARMED，不能立即盲布防 |
| 同 boot 重启守护、该 boot 已对账 | 恢复有效事务和缓存；不新建 BOOT 或消费旧 arm_id；若本 boot 新有 INTENT，继续 STAND_DOWN |
| 当前 source_boot_id 的 INTENT 尚未执行 | STAND_DOWN，不能视为上次开机意图；明确失败走 CANCEL，未知走可观察超时等待 |
| 跨 boot、有效未消费 INTENT(reboot) | RECONCILING → 清旧槽验证 → 一次消费及原因分类；按第 7.2 节写结论，再由预算/稳定门槛决定 DISARMED 或新 arm_id |
| 跨 boot、有效未消费 INTENT(off) | 同样先清残再消费；可信人为启动记 OFF_MANUAL，可信 RTC 关联记 OFF_RTC_WAKE，原因不足/冲突才记 OFF_OUTCOME_UNKNOWN。分类不依赖 REOFF 开关，只有第 7.4 节全满足才考虑补偿关机 |
| 无有效 INTENT、存在上 boot 已提交武装/HEARTBEAT | RECONCILING，先清残，再按第 7.2 节互斥分类；保守结算预算，不按心跳时间推断因果 |
| 旧 INTENT 已消费/被 CANCEL/属于旧实例代次或不匹配 arm_id | 不复用；已知完成项由快照水位去重，过旧/冲突项隔离，UNKNOWN 分支不自动关机 |
| 尾记录是 BOOT/RESCUE 或只有归档 | 从快照和有效事务归约未消费意图；没有有效布防则保持 DISARMED，材料不足为 UNKNOWN，不按末条类型续期 |
| ARM_PENDING 或核销中断 | 按第 5.3 节恢复；跨 boot 先清残，不把未提交布防当 HEARTBEAT 成功 |
| 清槽失败、读回不符或不可读 | FAULT，保留旧 arm_id、待清阶段和未完成消费；禁止新布防及 REOFF，不报告已解除 |
| 槽竞争、RTC 跳变、维护/停用/卸载 | 冲突为 QUARANTINE，其余 STAND_DOWN；提升停止代次；确认自有槽清除验证后保持停用，不自动恢复 |
| 预算耗尽、冷却/健康/电量/温度门槛不满足 | 禁止新布防；尝试清自有槽读回，到 DISARMED/STAND_DOWN；清失败 FAULT，等待条件与显式故障修复 |
| 明确修复/取消后获准 resume | 校验停止代次与所有门槛，创建新事务/arm_id；不复活旧意图，不重置故障预算冒充稳定运行 |

每次真实新 boot，尽早取得锁并冻结自动动作，读取而非先销毁证据，持久保存旧 arm_id、槽值/使能可见信息、bootreason 原值和恢复阶段；然后清旧自有槽并读回、持久 CLEARED_VERIFIED，最后提交 consumed_by_boot_id、预算结算和 BOOT 结论。读回空也不能当固件全部解除证明。归属未知按第 2/11 节可信恢复流程处理。BOOT 分类可以是未知，清残核销仍可独立完成；不以分类成功替代清槽成功。

### 7.2 原因分类：与第 9 节共用的唯一规则

boot_id 只标识内核启动；墙钟期限接近不证明 RTC 因果，同 boot 用单调时间，跨 boot 没有可信连续 RTC 时基时仅记可证范围或未知。bootreason 只作证据，必须经本机映射实测（T2/T3 待裁决，REOFF 另须 T6）。字段缺失、歧义或互相冲突时只记 UNKNOWN 类结论，不能假设手动或正常。

| 有效旧周期 | 充分且无冲突的证据 | 分类 |
| --- | --- | --- |
| INTENT(reboot) | 映射已验证的普通软件重启原因，关联本次登记，可信时基/阶段证据排除该笔 RTC 已触发 | REBOOT_OK |
| INTENT(reboot) | 已验证 RTC 唤醒原因，关联该 arm_id、目标及可信采样，且无外部槽冲突 | REBOOT_RESCUED |
| INTENT(reboot) | 任一关键证据缺失/矛盾，或是否已响不明 | REBOOT_OUTCOME_UNKNOWN |
| 无 INTENT、有已提交武装/HEARTBEAT | 已验证非 RTC 自恢复原因，可信 RTC 连续证据确认早于该笔实际触发，且无冲突 | SELF_RECOVERED |
| 无 INTENT、有已提交武装/HEARTBEAT | 明确 RTC 唤醒证据与该 arm_id 对应，且无冲突 | RESCUED_ABNORMAL |
| 无 INTENT、有已提交武装/HEARTBEAT | 其余情况（包括原因不明、异常后人工开机、时间依据不足） | ABNORMAL_OUTCOME_UNKNOWN；若有明确人工原因可附证据，不冒称 RTC 救起 |
| INTENT(off) | 映射已验证的电源键等人为启动且无 RTC 冲突 | OFF_MANUAL |
| INTENT(off) | 可信 RTC 关联证据 | OFF_RTC_WAKE，是否 REOFF 另由第 7.4 节决定 |
| INTENT(off) | 原因不明或冲突 | OFF_OUTCOME_UNKNOWN，保持开机、不自动关机 |

HEARTBEAT 的 SELF_RECOVERED 与 RESCUED_ABNORMAL 依赖相斥的原因及触发证据；均不满足或同时出现证据冲突则第三分支 UNKNOWN，不按「没到墙钟截止点」作覆盖式判断。

### 7.3 独立 RTC 救援预算与稳定复位

预算记录包括 incident_id、上限、已用/预留额度、关联保护会话、跨 boot 结算、稳定确认和冷却阶段，保存在权威账本/快照，不用 ATTEMPTS_MAX。设计起点 RTC_RESCUE_MAX=1：

1. 新保护会话在首次触碰硬件前持久预扣一份额度；同 boot 连续续期共用这份预留，不每分钟扣一次。PREPARED 中断也占用额度，不能靠漏记绕过。
2. 新 boot 清残对账后，RTC 救援或结果未知均将前一保护会话计为已用，重复 BOOT 不重复扣。只有清槽成功且有可信证据证明正常注销/普通重启、没有消耗救援时才可释放预留；不知道就不退。
3. 已用额度达到上限或无可供新会话预留的余额时，不接纳新保护会话，清自有槽读回，等待恢复；当前同 boot 已预留会话的正常续期不重复申请额度。不能在每次开机无条件恢复 +600。预算只约束新布防，不能保证对账前再崩溃或用户空间未启动时硬件不复响。
4. 救援/未知后，旧槽已清且本 boot 连续稳定运行 STABLE_RUN=1800 秒，并满足至少 COOLDOWN=1800 秒的本 boot 单调观察，才持久结束旧 incident 并复位到新预算。两计时可并行，任何崩溃、健康失败或 boot 变化都重新计时，不用墙钟跨 boot 抵扣冷却。
5. 稳定要求：boot_completed=1、对账已提交、守护持续健康、无写失败/槽冲突、RescueX 可核实健康条件无待处理救援、温度/电量可信且合格。RescueX 健康接口尚需离线约定，不能核实则不复位。普通缺进程或用户 resume 不能代替稳定确认。
6. 电量低于 20%、电池温度达到 45℃，或采样缺失/单位未验证，即停止布防、清自有槽并停用；恢复须指标合格并完成稳定观察，故障态仍须显式修复。传感器路径、单位和可用性为 T2/T3 待裁决；本机阈值的适用性须有人值守定版。

这是以一段无保护期换取耗电/热风险有界的取舍。新增数值是保守设计起点，不改变原有参数默认值，也不声称经真机验证。

### 7.4 REOFF 限次协议

REOFF 默认关闭，须 T6 必测通过才可显式启用。仅在有效跨 boot off 意图于本次对账前未消费、来源/arm_id/代次可验证、已验证且无歧义的本机 RTC 原因、清旧槽读回成功、无未知事务/维护/人工介入、资源与安全门槛均通过时允许。消费提交须把 REOFF 候选与本次 consumed_by_boot_id 绑定，只有该 boot 可继续候选；后续 boot 不因旧 off 已消费而再次补偿。未知原因一律保持开机。

先持久关闭续期并写关联原 off 事务的 REOFF_ATTEMPT（每个原事务最多 1 次，跨 boot 保留），提交后才发固定关机命令。发出前再次检查维护或可信人工取消；有介入则取消补偿并保持停用。仅能记录可观察的介入，不能假称可靠识别所有用户行为。请求在落盘后即计为已尝试，即使命令尚未执行便崩溃也不自动补发。清槽失败不执行；命令失败/超时/结果未知则 QUARANTINE，限频报警，不循环重试、不自动续期。REOFF 不新建唤醒，也不能恢复 G3 的绝对承诺。复关机实际结果、人工启动区分及响后残留仍为 T2/T3 待裁决，并由 T6 专项裁决。

## 8. 与 RescueX 的分工（防两个救兵打架）

职责保持不变：关机/充电层陷阱由本模块负责，卡米/开机循环由已在守护的 RescueX 主责；boot 镜像层由真人安全模式（RescueX 清单第 5 项未验）、双槽备份和 USB fastboot 处理。RTC 单写者目前只是合作策略，未证明 RescueX 或厂商绝不写槽。

真机布防前必须离线审阅 RescueX 动作与文件写集，列出 RTC/PowerOffAlarm 访问、重启/关机命令、模块禁用、状态清理与恢复脚本路径及健康标记契约；当前材料无这些实现，审阅未执行，不把共存基线当完成证明。RescueX 若禁用本模块，应调用同锁解除武装入口并读回；若不能合作，布防前解决该路径或保持本模块停用。绕过清理可能留下旧闹钟，不能指望下次禁用脚本收尾。RescueX 发起的重启若不经自有预登记按未登记路径处理，不伪称覆盖。

ATTEMPTS_MAX 备份禁用层默认关；只在显式决定转移主责并完成共存审阅后才能启用，不能因 RescueX 临时不可见自动启用。它与 RTC 预算完全独立。

bootmod 监督默认只报告；获显式许可拉活时，使用真实进程身份（启动时标/可执行身份，防 PID 复用）、同一锁、实例/升级代次和持久停用状态。STAND_DOWN、维护、FAULT、QUARANTINE、升级、禁用、卸载、未知状态时一律不拉活布防；不得清理状态或清掉 FAULT。拉活有退避和每 boot 次数上限，数值在主机监督模拟通过后定版，未定版保持只报告。监督不可用不阻止守护本身基本功能。

全系统竞争只采用第 2 节的冲突即停用策略，不允许「本轮不抢、下轮覆盖」。涉及不明外部槽时保留证据，可信入口解决冲突、清残验证并显式重新许可后才可用。

## 9. 场景时序

以下均为条件式预期，设备行为为 T2/T3 待裁决；原因分类严格复用第 7.2 节。

- A 正常重启：T0 预登记 INTENT(reboot, seq=42)，持久停止普通续期并请求 +240、读回提交 → 发普通重启命令 → 新 boot 先清残验证再消费 42 → 仅充分普通重启证据记 REBOOT_OK，是否可新布防由预算门槛决定。约 90 秒不是时限保证。
- B 重启落陷：同 A 但停在充电层 → 若通道保留且有效，到实际硬件目标触发上电 → 清残、消费 → RTC 与 arm_id 证据充分才记 REBOOT_RESCUED，否则 REBOOT_OUTCOME_UNKNOWN；结算救援预算，先稳定/冷却，不立即恢复续期。
- C 故意关机：受支持入口持久 stop_generation 和 INTENT(off, seq=43) → 清槽读回并提交 → 关机。本模块保持停用不主动重建；其他写者或固件残留风险不在绝对保证内。后来人工开机仍先清残，可信人为原因记 OFF_MANUAL，原因不明记 OFF_OUTCOME_UNKNOWN。
- D 无登记消失：最后已提交武装可能在理想续期下剩约 540–600 秒；失败/延迟可能更短或已无闹钟 → 若有效则尝试触发 → 清残对账，按互斥证据记 SELF_RECOVERED、RESCUED_ABNORMAL 或 ABNORMAL_OUTCOME_UNKNOWN，不按心跳墙钟估算因果；救援/未知消耗预算。
- E 注销失败误响：off PREPARED 已持久但清槽失败，受支持入口应已返回失败；若随后外部路径仍关机并被拉起 → 先清旧槽并验证 → 未通过 T6 或原因不明时保持开机、停用和报警；只有第 7.4 节全满足才一次 REOFF。命令失败不循环。
- F 登记后取消或守护同 boot 拉活：保留本 boot 意图不消费；可信失败确认后 CANCEL、清残，再显式 resume；结果未知保持可观察 STAND_DOWN，不因超时自行重布防。

| 清后写失败、强杀或磁盘失败 | 可能漏救或留下未提交武装；按阶段恢复并显示实际剩余/未知，不保证旧值还在或至多响一次 |
| off 漏登记/清槽失败 | 可能误启动；只有支持入口成功注销具 G3 条件承诺。REOFF 不抹去已发生的误启动 |
| 状态目录被删/不可读、账本损坏或整体回滚 | UNKNOWN，停止自动动作，读取硬件；确认自有旧槽清除读回，无法确认归属则待可信恢复入口确认后清除验证。清后仍保持停用、隔离旧意图，不能重建后立即布防或猜用户想关机。目录删除时旧进程也须在共享锁下停止，监督不得创建新实例绕过 |

| 救起后再次崩溃、低电量/高温 | 先预扣的独立预算、稳定运行复位和冷却；耗尽/门槛失败清槽停用。仍可能在早期清残前再次崩溃，用户空间未运行时不能由软件补救；硬件复响为 T2/T3 待裁决 |
| REOFF 命令失败或原因误判 | 默认关闭，T6 必测；一次持久请求、未知保持开机，失败隔离限频报警，不循环关机 |
| RescueX/监督绕过协议、强删/离线禁用 | 可能残留武装；必须生命周期收尾及离线写集审阅，具体残余风险见第 13.2 节 |
| RTC 真失供电、系统持续挂死 | 不覆盖；插电及 ACC 75–80 守护的既有常态不构成保证，不无限重试 |

只读空槽、过期比较值、驱动 alarm enable、PMIC 中断和固件关机唤醒状态不是同一证据。响后、回拨后旧值再入未来是否能重触发、清槽对应的固件效果为 T2/T3 待裁决。软件预算约束新增武装，不能代替硬件一次性验证。

## 12. 验证计划（逐级、互不叠风险）

T1 更名为「无重启读写清探针」，它修改全局槽，不是只读或天然无害。已有本次结果见第 12.5 节；本轮未运行任何探针或模块。未来复用必须先校验初值可读、检查每步退出码，用受检 finally 执行经校验的尽力恢复，旧绝对值恢复前须确认未过期、时基及归属可信；失败不许声称恢复保证。不得直接复制现有探针为生产事务，本轮不修改探针。

### 13.2 升级、禁用、卸载的解除武装协议

1. 所有生命周期入口先持同一锁，持久增加 stop_generation，禁止旧实例续期及监督拉活，登记生命周期操作和实例/升级代次；通知守护停止，不能仅发 SIGTERM 就假设完成。
2. 保存旧 arm_id 与阶段，清自有 wakealarm 并读回；未知归属按可信恢复流程确认，清不掉或不可读不报成功。COMMITTED 后保持 DISARMED/停用，向调用者返回可核对的空槽结果、事务身份和失败待办。
3. 升级仅在旧实例停止、清残验证提交后迁移权威状态，保留预算、消费身份和停止代次；未知版本隔离旧 INTENT，失败保持停用可恢复，不自动启新代。新代启动重新校验锁与账本，显式许可后才可布防。
4. 禁用必须在脚本失效前完成解除武装；不能依赖下一 boot 执行已禁用模块。卸载在清槽提交后才删除模块执行文件；保留最小停用/收尾结果供核对，并撤销监督许可。失败时保留可用清理入口和状态，提示真人完成，不继续删除。
5. 用户强删目录、Magisk/其他模块离线禁用、RescueX 绕过接口或卸载脚本不运行时，旧武装可能残留，已删除守护无法收尾。明确要求操作前先停用并检查空槽；若绕过，须真人通过可信 root 清理入口/经审阅的人工清槽步骤验证，并在问题解决前避免无人值守关机。不能承诺残留至多响一次；固件状态与调时后复响仍为 T2/T3 待裁决。

以上为未来实现和验证协议，不是本轮手机操作指令的执行记录。
