# DeadMan Rescue 设计审计

## 总 verdict：需改后开发

本轮是设计审计交付，不是模块或真机验收。已通读 AUDIT-BRIEF.md、DESIGN.md 全文（含 12.5）、PREP-REPORT.md、probe-rtc.js 和 probe-rtc-result.json；未联网、未操作手机、未执行探针或模块代码。审计接受简报中的既定事实，不重新质疑故障原型、RTC root 读写能力、RescueX 已运行等事实。

T1 足以支持继续设计 RTC 方案，不能支持直接安装具备自动关机和持续布防能力的 P1。先修订下述 BLOCKER，再开发主机状态机与故障注入验证；真机布防需通过有人值守的 T2/T3 门槛。G1、G3、G4 当前都不能按绝对承诺验收。尤其“清除失败后再自动关机”只能补偿一次误启动，不能实现“故意关机绝不被拉起”。

证据边界：原始结果显示 uid=0、rtc-pm8xxx、初始槽为空、写 +7200 成功且读回 11143、此前 since_epoch=3942、清除后为空。差值 7201 与采样间隔相容，但不是同时刻采样或漂移测量。sys.powerctl 为空只是运行期基线。PowerOffAlarm 在机不等于已验证其调用、调度或关机唤醒行为。本文涉及 Android/init/RTC 的一般机制判断不替代本机源码或实测；设备特有行为标为“推测”或“T2/T3 待裁决”。

## 分级发现清单

### F01 · BLOCKER · 第 1、6、7、9 节：G3 与拦截覆盖不成立

问题：Magisk 拉起的 shell 守护不因此就成为 Android init 可按预期优雅终止的独立服务。init 的关机终止流程可能发信号、受超时约束并最终强杀；具体进程树、进程组、服务属性以及 shell 正在等待子命令的状态均影响 trap。不能由“系统关机”推导出“本守护必先收到可执行的 SIGTERM”。登记漏掉后第 7 节只能等开机补偿，已违反 G3。

触发：系统菜单关机、厂商快捷入口、进程被强杀、关机过快或磁盘阻塞。

建议：将自有预登记接口列为唯一具有条件保证的主路；trap 作为尽力补充。明确普通菜单入口覆盖边界，在完成本机生命周期采样前不得声称全面拦截。G3 改为“受支持入口在注销读回成功后保证不由本模块主动保留闹钟；其他路径存在误启动风险”。本机时序与 bootreason 为 T2/T3 待裁决。

### F02 · BLOCKER · 第 4、5、7 节：文件原子性不等于跨 RTC 事务

问题：state、registry、seq 及硬件槽不可能靠各文件 rename 自动实现一致提交；追加账本与“所有状态文件临时文件替换”也未定义关系。清零后写入前被杀会漏救；布防后心跳落盘前被杀会出现未记账武装；对账核销后清槽前断电可能丢失重试依据。

触发：任意上述窗口中断电、SIGKILL、ENOSPC 或 I/O 错误；两个入口并发。

建议：统一单写者锁和事务编号，定义持久 PREPARED → 硬件操作及读回 → COMMITTED/FAULT；重放按操作幂等处理。off 必须先持久禁止续期，再清槽、验证、提交；恢复见不确定事务先停自动动作并读硬件。明确每一崩溃点的恢复策略和无法原子消除的无闹钟窗口。

### F03 · BLOCKER · 第 1、7、9、11 节：G4 被过度推导

问题：T1 没有观察闹钟触发后状态。RTC core 的可见 alarm 值、驱动 alarm enable、PMIC 中断与固件开机处理不是同一状态，不能仅凭“到过点”证明禁用；时钟回拨或 RTC 重设后，保留的比较值还可能再次成为未来值（是否重新触发取决于硬件使能，推测）。第 7 节自动恢复续期本身也会产生下一笔唤醒，不能防救起后再次崩溃的循环。

触发：触发后残留、清除失败、对账前再次崩溃、REOFF 命令失败或救起立即重布防。

建议：把 G4 拆成“每个 arm_id 只核销一次”和“硬件一次性需实测”；启动先清旧槽并验证，再决定是否新布防。引入跨 boot 的救援预算和稳定运行后的复位条件；对账不确定时禁止自动再关机。响后状态与复关机结果为 T2/T3 待裁决。

### F04 · MAJOR · 第 5、7、9 节：状态分支和身份约束缺失

问题：HEARTBEAT 两分支重叠；第 7 节把所有 reboot 都记 REBOOT_OK，第 9 节却存在 REBOOT_RESCUED；未定义账本为空、尾部为 BOOT/RESCUE、同 boot 重启守护、同 boot 预登记后未关机、旧 INTENT、seq 损坏/回滚以及 state 与账本冲突。

触发：首次安装、重装、守护拉活、关机取消、恢复备份、日志轮转及中断。

建议：不用“末条 type”代替状态机，按有效事务和 consumed_by_boot_id 归约；INTENT 绑定来源 boot_id 与 arm_id；同 boot 不得冒充下一次启动核销。增加 UNKNOWN、DISARMED、ARM_PENDING、ARMED、STAND_DOWN、RECONCILING、FAULT、QUARANTINE 等明确状态。无法验证的恢复不自动关机。

### F05 · MAJOR · 第 2、4、11、12.5 节：相对写入不保证武装期间免疫调时

问题：+秒数只避免写入时误用系统 epoch。若之后硬件 RTC 被重设，闹钟仍用旧比较值，期限可能提前或延后。每 60 秒自校正不覆盖停机、守护被杀与关机过渡。先清后写也会释放唯一槽位。

触发：time_daemon/用户/网络调时最终触及 RTC，或厂商组件在关机时重写/清槽（本机是否发生为推测）。

建议：删除“免疫”“只影响日志”的承诺；记录 RTC 和本 boot 单调时钟配对采样，识别跳变；外部槽变更进入冲突状态，不能既称“不抢回”又在下轮覆盖。关机过渡保留性与厂商竞争为 T2/T3 待裁决。

### F06 · MAJOR · 第 3、8、11 节：单写者尚只是策略

问题：材料只有 RescueX 安装与运行基线，没有其动作实现；无法证明其不碰 RTC、不会禁用本模块或重启设备。bootmod 拉活可在 STAND_DOWN、卸载或 FAULT 后重新布防。

触发：RescueX 救援、模块禁用/恢复、监督器误判和多实例。

建议：补 RescueX 动作与文件写集的离线审阅；守护、命令入口、监督器共享同一锁和持久停用状态。监督器只报告或按显式许可拉活，不得替停用模块布防。计数器备份层默认关闭正确。

### F07 · MAJOR · 第 3、5、10、11 节：资源与故障恢复预算未落地

问题：只有“日志轮转”，追加账本和归档无上限；状态目录被删除、满盘、fsync 失败、三次写失败后旧 alarm 状态均未定义。ATTEMPTS_MAX 属于禁用模块备份层，不能充当 RTC 救援次数预算。

触发：长期运行、清理类模块、存储满、重复救援。

建议：账本快照加有界尾日志，配置字节/文件上限并保留未完成事务；状态丢失进入 UNKNOWN，读取并清旧槽验证，不猜测用户关机意图。增加独立救援预算、冷却、低电量/高温停用策略以及可观察的 FAULT。

### F08 · MAJOR · 第 3、6、13 节：升级卸载与 root 输入边界缺失

问题：卸载、禁用、升级和监督器有并发；卸载脚本不运行时仍可能留下武装。root shell 若 source 状态或拼接参数可扩大攻击面。

触发：用户直接删除模块、Magisk 禁用、升级失败、伪造状态/符号链接/命令参数。

建议：root:root 目录 0700、文件 0600、umask 077；固定绝对路径，拒绝链接及异常所有者，状态只按数据解析，不 eval/source，不暴露无鉴权广播或可写命令队列。卸载/禁用先持久停用监督和续期、清槽读回、提交再删除；失败明确保留待处理状态。强删后残留无法靠已删除守护收尾，必须文档化为有条件的残余风险。

### F09 · MINOR · 第 10、12、13 节及探针：参数和阶段名称误导

问题：G1 把“触发上电”写成“进系统”；T1 名为只读实际有写；P1 已会改全局唤醒槽；探针的 fail-closed 注释不等于异常安全恢复。

触发：把测试标签当能力保证或直接照搬探针为生产代码。

建议：区分触发时限与健康启动时限、直写与厂商通道参数；P1 先只读/模拟，真机布防另设门槛。探针恢复逻辑放入受检的 finally，检查每步返回值，但本轮不修改探针。

### F10 · NOTE · 第 12.5 节、PREP-REPORT 阶段二

问题：T1 原始结果可信支持本次读写清，不支持长期独占、关机保留或异常路径恢复。probe-rtc.js 中 shell 返回非零不会自动 throw；读取初值失败仍可能继续清写，异常也未必恢复旧 alarm；旧绝对值恢复前可能已过期。本次原槽为空且所有关键调用成功，不影响本次 T1 结论。

触发：未来复用探针遇到已有闹钟或失败。

建议：保留本次证据，限制其证明范围；将“恢复保证”改为经校验的尽力恢复，禁止直接复用为生产事务。

## 逐项回应审计范围 1–9

### 1. 状态机与对账逻辑

结论：不完备且存在竞态，须按 F02/F04 修订。

| 情况 | 当前缺口 | 所需确定规则 |
| --- | --- | --- |
| 对账清槽/核销中途断电 | 无事务恢复点 | 保存旧 arm_id 和处理阶段；下 boot 先验证清槽，再完成消费提交 |
| 续期清零后被杀 | 最后一笔也消失 | 标 ARM_PENDING/FAULT，承认无保护窗口；能否减少窗口须评估驱动接口，不能假定原子替换可用 |
| 新闹钟写完、心跳未记 | 硬件与账本不符 | PREPARED 含目标和采样；恢复读回，禁止凭最后心跳盲判 |
| INTENT(reboot) 后闹钟已响 | 第 7/9 节矛盾 | 核销与原因分类分离；bootreason、RTC 采样及期限仅提供证据，原因不明记 REBOOT_OUTCOME_UNKNOWN |
| seq 损坏/回滚 | 单调性无实施依据 | 校验完整记录、版本、事务链和快照代次；只取已验证最大 seq；无法排除回滚则建立新实例代次并隔离旧意图 |
| 同 boot_id 重复启动守护 | 可能把当前意图吃掉 | BOOT 对账每 boot 幂等；当前 boot 的 INTENT 保留，不当成上次启动登记 |
| 旧 INTENT/空账本/末条 BOOT 或 RESCUE | 无分支 | 从快照与有效事务归约；缺失、坏尾、状态冲突各有 UNKNOWN 路径 |
| 预登记成功但重启/关机未执行 | 永久 stand-down | 命令返回失败即明确取消事务；结果未知不擅自续期；设置可观测超时等待人工或可信控制入口确认 |
| trap 与续期并发 | off 后可能再次被武装 | 所有写槽操作持同一锁，锁内复核 stop_generation；trap 等锁时间计入关机预算 |

追加日志须规定完整行/长度/校验与坏尾截断逻辑；snapshot 的临时文件需 fsync 后 rename，再 fsync 父目录。多个文件仍不能同步提交，应指定唯一权威记录，其他为可重建缓存。单调 seq 不能在任意外部备份整体回滚后得到绝对保证，应明确这一故障边界。boot_id 表示本次内核启动，不证明手动启动或救援原因；同 boot 内耗时用单调时钟，不用墙钟推算离线时长。跨 boot 没有可信连续时基时，只报告范围或未知。

### 2. 只触发一次的保证

结论：推翻现稿对 G4 的无条件证明，并非断言硬件必然重复触发。T1 只做未来设闹及清除；未观察 alarm 到点后 wakealarm 为空、过去值或禁用状态。即使 wakealarm 为空也不能直接证明固件所有关机唤醒状态均已清。

应区分：硬件单次中断、单 arm_id 的处理幂等、整次故障的救援次数。旧值已过期不等于已解除；RTC 回拨后旧值重入未来是否仍有效为推测，需观测 alarm enable/驱动可见信息并在 T2/T3 裁决。若 REOFF 清槽失败则不得把清零当成功；若再关机命令失败应留在停用/隔离态、限次报警，不能循环调用。若对账前再崩溃，late_start 尚未执行，需尽早的轻量清残策略和跨 boot 救援预算；这仍无法保证从不进入用户空间时的软件补救。

验收可承诺“持久化 arm_id 消费一次；成功读回清槽后不复用旧 arm_id；连续救援预算耗尽不再自动布防”，硬件一次性另列 T2/T3 待裁决。

### 3. 关机拦截可靠性

结论：SIGTERM 不宜作为主保证，见 F01。Android init 对 sys.powerctl 有专门处理，不能把属性读取当可靠、持久的关机事件日志；PREP 仅证实运行中为空。init 是否发到该 Magisk 子守护、trap 是否在 sleep/子命令退出前执行，以及属性是否仍能读取，均缺实机证据，T2/T3 待裁决。

解析至少按逗号拆动作与目标：shutdown 及 shutdown,<reason>，reboot 及 reboot,<target/reason>；具体厂商集合未知，不可只做字符串等号。reboot,recovery、reboot,bootloader 等应专门 STAND_DOWN/清槽，避免干扰人为刷机或维护，不能统一改签 +240；unknown target 采用已定义的保守策略，不能猜成普通重启。不得由“SIGTERM 到来”本身推断关机，普通停止/升级也能发此信号。

预登记只覆盖调用自有入口的操作，不覆盖厂商 UI、其他 root 调用、内核崩溃和强制断电。强制断电按异常救援符合目标，但“用户长按想关机”与“异常消失”对本模块可能不可区分，需提供明确停用后强关的流程。

临终路径涉及锁、持久记录、清槽/改签、读回、fsync 和目录同步，绝非保证“一次写盘、毫秒级”。必须量测分位耗时和最坏超时，提前创建目录/验证权限；trap 不等待网络、不做轮转、不长等锁。超时、EIO、ENOSPC 时返回失败并记录可恢复阶段。不得声称在不可控强杀前一定能完成。

### 4. RTC 通道风险

结论：相对偏移在写入当刻成立，不能扩大为全生命周期免疫。

| 风险 | 现在可规避/检测 | 仍需裁决 |
| --- | --- | --- |
| 系统调时最终重设 RTC | 删除免疫承诺；RTC/单调时钟配对，跳变进入异常态 | 本机调时是否触及 RTC、闹钟是否被同步调整：T2/T3 待裁决 |
| RTC 漂移或重置 | 读回容差、记录漂移范围，不拿墙钟绝对值写槽 | 长时间关机、充电层漂移及 RTC 保存性：T2/T3 待裁决 |
| PowerOffAlarm/其他组件覆盖 | 关闭已知用户功能；周期检查；明确冲突停用或显式独占策略 | 关机末期隐式写入、固件认哪个状态：T2/T3 待裁决 |
| 关机过渡清槽 | 可在预登记前后留证据，不把最后读回当关机后证明 | T2 正常 shutdown 与插电充电层分别验证；T3 取消路径复核 |
| 清后写窗口、外部抢槽 | 锁只保证本模块内部；减少操作链并记录失败阶段 | 能否使用其他更新接口须核实，本轮未验证，不预设可用 |

RTC 漂移与系统校时为两种问题；运行期每分钟续期只限制作业正常时的误差累积。PowerOffAlarm 备选不是只换一条命令，可能涉及私有持久状态与关机侧逻辑，切换通道必须有独立契约和重复 T2/T3，禁止两路同时兜底竞争。

### 5. 共存与分工

结论：职责划分合理，执行单写者尚未证明。既定事实是 RescueX 在守护，不应重复质疑其存在；但现有材料没有其源码/脚本动作，不能据模块名证明不写 RTC。需离线核对其重启、关机、禁用模块、清理状态和恢复脚本路径。即便不写 RTC，禁用本模块仍可留下上一笔唤醒；RescueX 发起重启也会绕过预登记。

备份计数层默认关正确，不能在 RescueX 临时不可见时自动启用；切换应显式并保持一个禁用模块的主责。bootmod 顺带监督有启动依赖和重启风暴风险：使用真实进程身份与单实例锁，尊重停用、维护、FAULT、STAND_DOWN、升级代次；加退避与启动次数上限。外部监督不可用不应阻止守护自身基本功能，监督器也不得擅自清理状态。

### 6. 失效模式与最坏情况

| 模式 | 触发条件与最坏后果 | 当前缓解评价及所需改法 |
| --- | --- | --- |
| 误救 | off 漏登记、清槽失败或覆盖后残留；关机后启动 | 第 7 节只补偿且可能误识原因；不足。支持入口先确认注销，未知原因禁止自动关机，披露 G3 条件 |
| 漏救 | 清后写失败、被杀、外部清槽、时钟跳变、固件不认、服务未启动 | 三次失败停续期不足；需单次状态/保护剩余量、明确报警、T2 门槛及失效可观测性 |
| 救起—崩溃—再救 | 每次启动均恢复 +600，故障持续 | 当前无次数边界；耗电、发热、插电反复上电。独立跨 boot 救援预算、冷却及健康运行后复位；预算耗尽清槽并停止自动救援，承认可用性取舍 |
| REOFF 循环/误关 | 原因映射不准、失败重试、用户中途操作 | 可选 T6 不足；精确可信映射、每事务至多一次自动关机、维护/人工介入取消、失败隔离 |
| 无限增长 | 心跳、账本、归档和异常刷日志 | 只有日志轮转，不足；字节上限、限频、压缩快照、保留待完成事务并测试 ENOSPC |
| 状态被清理误删 | 清理模块/root 操作删除独立目录 | 放模块外仅防升级丢失；不足。目录权限、清理排除说明、缺失检测与 UNKNOWN，禁止重建后立即盲目布防或关机 |
| 真耗尽/持续挂死 | RTC 不保电或系统不进可恢复关机态 | 已声明边界合理；不把插电常态当保证，不将恢复失败无限重试 |

状态写盘失败时“继续武装”与“停止救援”存在可用性/误救取舍，须明确默认策略。不能承诺所有故障下同时绝不误救、绝不漏救。

### 7. 参数审计

结论：可作起始试验参数，不能视为定版。

直写 sysfs 的理想连续续期下，故障发生时距下一闹钟约 540–600 秒（不含调度/写入延迟）；600 秒是唤醒触发上界，不是进入系统上界，后者还需约 60–120 秒或更久。三次写失败、暂停或调度延迟会破坏该区间；清后写失败甚至没有闹钟。因此 G1 应区分“到点发起唤醒”和“系统健康完成启动”，若要求十分钟内进系统需从窗口扣除启动与抖动预算。

高通组件“减一分钟、拒绝一分钟内”的事实应仅用于该通道，T1 没证明直写也有此变换。若目标 +240 最终被减为 +180，则对 120 秒正常启动仅剩约 60 秒余量；拒绝条件应按变换前后分别校验，具体 API 口径未验证，不可双减一分钟。WINDOW=600 若走该通道也需换算实际期限。偏移下限 240 与 REBOOT_WAKE=240 表面一致，但只是输入值下限；需定义为“最终硬件剩余量”还是“通道请求量”。

RENEW=60 相比 WINDOW=600 留有多轮余量合理，但应按单调时钟调度并评估执行耗时；读回允许采样流逝容差，不接受任意偏差。读回比较使用 RTC 差值；记录采样前后值形成区间，避免串行采样的 1 秒被误判。特殊重启目标不应适用正常 REBOOT_WAKE。

### 9. 安全面

结论：root 常驻能服务于本目标，但应收缩解释与控制入口，并补生命周期协议。最小权限见 F08；本模块不能隔离恶意 root，也无法阻止其他合法 root 写同一槽。锁只约束合作进程，不能当硬件独占授权。

对状态字段做类型、范围、版本、boot_id/arm_id 关联检查；日志不得被解释执行。配置文件需 root 所有且不可被普通 app 写；路径固定，临时文件安全创建在同目录，拒绝软链接，避免对可写外部目录 chmod/chown。若由 AutoJs/Muse 调用 root 入口，应限定命令及参数，不以普通可写文件作为 root 指令来源。不需要增加网络监听或外发日志。

升级先停用旧实例和监督、清旧槽验证，再迁移状态；未知版本不得按旧 INTENT 自动关机。卸载正常路径应清槽后给出可核对结果；禁用也需有明确解除武装步骤，不能依赖下次 boot 执行已经禁用的脚本。卸载后只留一次闹钟，可能违背用户关机意愿，并可能在厂商状态或调时条件下不止一次，因此不能无条件接受。若强删/离线禁用绕过收尾，软件无法保证清除；应明确要求卸载前停用并检查空槽，失败保留清理入口/记录并提示真人收尾。没有本机响后行为证据前，不承诺“至多响一次”。
